# Bit 08 — I/O: media types, headers, cache, errors

Closes: A1 (open media types + request binary) · A2 (typed response headers) · A4 (Last-Modified/cache-control) · A7 (problem+json).
Oracle kept green: `tests/integration/response.test.ts`, `tests/integration/errors.test.ts`, `tests/integration/validation.test.ts`.

## Scope
The rich I/O capabilities declared on top of the response/error core. **The core itself — `response/response.ts`, `response/builder.ts`, `errors/{error,errors,projector}.ts` — is born at bit 02** (dispatch needs it; dependency re-cut). This bit **adds cases to those born-at-02 files** (RAW_BODY, output validation, exact-essence content-type, media-type affinity) and owns the capabilities around them. `.output()` opens to any `type/subtype`; a non-known media type is a typed bytes body (`format: binary`) carrying its content-type to the IR; per-status response headers become declarable/typed; `Last-Modified`/`cacheControl`; opt-in problem+json; and the request `binary` slot.

## Perf discipline (pinned — must not regress, v0 already optimal here)
- `response/output-validation.test.ts` — output validation runs from the **retained raw** body (no clone, no tee) in the common case; a honey-produced stream (sse/stream/generate) is **never buffered**; `response.clone()` is the last-resort branch only when the raw was not retained. Input body is read **once** (validation), the handler gets the typed value and never re-reads it; `bodyLimit` wraps with one `new Request(req, init)`, no body copy. The `Request` is never cloned per hop. The hot-path gate's json/param/large-response scenarios cover this.

## Perf (v1 improvements — from the audit)
- **RAW_BODY output-validation reader (H18.1).** The unconditional `WeakMap<Response, raw>` *write* is born with `response.ts`/`builder.ts` at **bit 02** (replacing v0's `Object.defineProperty(response, RAW_BODY)` on every buffered 2xx — `response.ts:101` — which is slow on a host object and shape-perturbing; the WeakMap pays no per-response `defineProperty`, the perf win, applied at birth). **Bit 08 adds the output-validation reader** (`validate-output` runs the JSON output schema from the retained raw, no clone) + the HEAD `content-length` reader (`body-kind.ts`). The write being unconditional is what lets these readers — plus `compress` (bit 07) and `ctx.res.raw(honeyResponse)` (bit 02) — all find the raw on the default output-validation-off path; the discarded `ov !== null || node` gate would have broken them.
- **Validation sync spine.** `validateInput`/`validateOutput` are `async` and insert a `.then()` even for params/query/headers routes that read no body and use a sync validator (`validation.ts:342`, `index.ts:1425`) — forcing a needless microtask. v1 stays sync when the validator and the route are sync.
- **Encoder singletons.** `new TextEncoder()`/`new TextDecoder()` are created per call in sse/stream/binary/output-validate (`response.ts:216,295`, `honey-response.ts`, `index.ts:2878`, `body-kind.ts:58`); v1 uses module singletons.

## Cases (expected results — pin so two implementers don't diverge)

| area | case | result |
| --- | --- | --- |
| problem+json | mapping (pinned, R2) | `type` = `https://honey.dev/errors/{errorKey}`; `title` = the status reason phrase from a frozen table (RFC 9110 phrasing, e.g. 422 "Unprocessable Content", never title-cased keys); `status` = HTTP status; `detail` = `HoneyError.message`; `instance` = the request id when `requestId()` ran, else omitted, never from an inbound header; honey's `fields` ride as an RFC 9457 **extension member** `errors` (present only when non-empty, nested so a field named `status`/`type` cannot collide with a top-level member); `vars` stay server-side as in the native envelope (message-template inputs, possibly internal), so problem mode leaks no more than the default. Schema errors (`error.data`) keep their declared `application/json` contract through the custom formatter, not reshaped into a problem document |
| problem+json | opt-in off | native honey error-key JSON (`{ error_key, fields, message, status, status_key, success }`) unchanged |
| range | `Range: bytes=0-99` on a 500-byte body | 206 + `Content-Range: bytes 0-99/500` + `Accept-Ranges: bytes` |
| range | `Range: bytes=600-700` (past end) | 416 + `Content-Range: bytes */500` |
| range | no `Range` | 200, full body |
| range | `Range` on a stream with unknown length | 200 (range declined), no 206 |
| media type | declared `image/gif` produced | typed bytes body; no JSON validation |
| media type | produced `application/json5` vs declared `application/json` | content-type mismatch (exact essence) → 500 |
