## Scope
The three runtime adapters and a **plain `serve(app, options)`**. Each adapter may use only its runtime's builtins (`00-rules.md` environments); the portable core never imports an adapter — which is why `serve` is an explicit import (`@lovrozagar/honey/serve`), **not** an `app.serve()` method (a core method reaching an adapter would need the forbidden slot — H23). The v0 serve-slot/serve-register/feature-load/feature-detect machinery (a module slot + `enableServe()`-at-import + build-time source scanning to inject prelude imports) is **cut** — same self-registering pattern H23 forbids. `serve(app)` detects the runtime and calls the node or bun adapter, returning a handle `{ close(timeout?), hostname, port, runtime, url }` (the Node server's `shutdown(timeout?)` stays on `./node`). **Workers has no adapter module** (`export default app` — `app.fetch(request, env, ctx)` is already the Workers signature; v0's `workers/serve.ts` was only an "export fetch" throw, dropped). `serve` options: `env`, `hostname` (default `0.0.0.0`), `port` (default `3000`), `maxRequestBodySize`, `headersTimeout`/`requestTimeout`/`keepAliveTimeout`, `onError`. **Dropped from v0:** the `cors` serve-option (it set module-global state via `_setGlobal`; CORS is only `app.use(cors())` — H23) and the `runtime` override (detection is exact, so an override can only pick the wrong adapter). The `maxRequestBodySize` default (128 MiB) lives in the **shared serve options**, not `node/request.ts` — so Bun reads it (passed to `Bun.serve`) and Node enforces it without Bun importing `node:*`. `upgradeTimeout` + ws wiring are bit 06. The node adapter sets `PEER_ADDRESS` from the socket, feeding bit-03 `ctx.ip`; it registers no `'upgrade'` listener here (Upgrade requests serve as normal; the ws upgrade path is bit 06). `detect-runtime` is node/bun/cf only (no Deno). `honey init` scaffolding is bit 19 (honey's dev CLI, not an adapter). `optional-peer` guard is bit 06 (its only caller is ws's `ws` load).

**Codegen guard (no globalThis flag).** The generator imports the app module and a top-level `await serve(app)` must not bind a port. v0 used a `globalThis` CODEGEN flag (module-global state — forbidden). v1: the app module **exports** the app and does not serve at import (convention; serving lives in a separate entry or behind `import.meta.main`), so codegen reads the exported app without serving; if a signal is still needed, `serve()` reads an explicit `process.env.HONEY_CODEGEN` (explicit env, not module state), never a global. Finalized at the codegen bit.

**Serve behavior pins (bit 04, H22 — v1's actual behavior).**
- Default `onError` (no app handler, serve-level failure like a rejected `fetch`, a CR/LF header value, a stream that fails after headers): `process.emitWarning(error, "HoneyAdapterError")` — visible on stderr, silenceable with `--no-warnings`, observable via `process.on('warning')`, not `console` (no-console), not a swallow, not a crash. Routes through the logger at bit 07.
- Graceful shutdown: the drain's observable effect is **the app never runs work for a request that arrives after `shutdown()`** — in-flight answers drain and go out with `Connection: close`, idle keep-alives are closed, post-shutdown requests on a live connection are dropped (not answered 503). v0's draining 503 does not reach the wire (verified on real sockets); v1 pins the real behavior. After the drain timeout, stuck work is aborted with "The server is shutting down" and connections are cut.
- The adapter's own `400`/`500`/`503` answers carry their reason phrase **explicitly** (v1 fix): Node's `writeHead` sets `statusMessage` before it validates headers, so a header-validation throw (a CR/LF value) would otherwise emit the inherited status line `HTTP/1.1 500 OK`. Pinned with the full status line.
- Hop-by-hop headers (and any header `Connection` names) are dropped on BOTH a native `Response` and a `HoneyResponse` header map — core never strips them, so a handler-set `transfer-encoding` beside Node's `content-length` would otherwise put two framings on the wire (one key scan, no allocation). No `101`/`Upgrade` keep here; that path is bit 06.

## Security corpus
- request smuggling / header-injection at the `node:http` bridge; oversized header set (431).
- **Duplicate `Host` → 400 (RFC 9112 §3.2, v1 fix).** Node's parser accepts two `Host` headers; `req.headers.host` keeps the first while a distinct read sees both, so the URL and the Host the app sees disagree — the classic Host-ambiguity smuggling setup. `node/url.ts` rejects any request with more than one `Host` line (one pass over `rawHeaders`, no distinct-map build), absolute-form included, before the app runs. The other probes (CL+TE, duplicate CL, obs-fold, "chunked, identity", bare LF, space-before-colon) already fail in Node's parser and are pinned.

## Budget
- perf: adapter overhead gated by `bench/src/adapter.ts` — it serves each scenario three ways on loopback (a bare `node:http` handler = raw, v0's adapter, v1's), pipelining 400-request keep-alive batches so the server's work dominates. The **gate is v1 ≤ v0 × 1.10, significance-gated** (like `finalize.ts`; v0 is frozen, so this is a stable fixed-reference, machine-independent, no baseline file — a raw *ceiling* is not gated because the bridge legitimately costs ~1.5–3× a bare handler for URL canonicalization / request view / header filtering, a number with no principle). `v1/raw` is **reported** per scenario for visibility. Runs on Node (`node --conditions=honey-source`; under Bun, `node:http` is Bun's own impl and says nothing about Node users).
