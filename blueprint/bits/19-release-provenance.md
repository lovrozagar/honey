## Scope
Publish both packages and the generated SDKs correctly. Split v0 `plugin.ts` 864 / `build/index.ts` into `core/build/`. Under H9 nothing new is published as a runtime package, so provenance is scoped to the two packages that ship: `@lovrozagar/honey` and `@lovrozagar/honey-codegen` (npm provenance). Generated SDKs carry vendored runtime; their publication is the API author's pipeline, documented.

**core/build is a build-time consumer of `honey-codegen` (H18.5).** `build/plugin.ts` calls `generateTypes` and `generateRouteTree*` (homed at `gen/emit/ts/{type-gen,route-tree}.ts`), so it imports `@lovrozagar/honey-codegen` on the build path. This does not violate H1's lean *runtime* core — it is a `devDependency`/build-time import, never shipped to a serving request — but it is stated here so the dependency is explicit. (Alternative considered: move the build plugin to `honey-codegen`; rejected because `honey()` apps call `honey/plugin` by convention.)

**Cutover + real `prod` e2e (H14/H21).** The atomic workspace swap lands here (`_v0` leaves `workspaces`, `packages/core` joins as `@lovrozagar/honey`), and this bit owns the consumer e2e passing identically against v1. v0's `--mode prod` was a no-op grep swap (verified bit 00; `prod ≡ dev`, `cf` always local); v1 makes it real: `prod` builds each app and drives the full Playwright suite against the **served built bundle** (request-time parity of the shipped artifact — beyond `test:build`'s import smoke), and `cf prod` deploys a worker (CF creds, CI). Re-record `blueprint/baselines/e2e-expected.json` against v1, move the 5 `cf-prod` cells to CI, and add the ≥1 genuine `@prod-only` assertion that makes `prod` distinct from `dev`.

**Cross-SDK auth-config consistency sweep (surfaced bit 12, G/F2).** The SDKs diverge by target on how the auth header is configured: Go/Rust/the Go CLI/Python (bit 14 c) read `IR.auth` (the spec's security scheme) to default the header name and prefix, and C#/Java are ruled to read it too (bits 15/16); **TS alone** exposes only `authHeaderName`/`authHeaderPrefix` config with hard defaults `Authorization`/`Bearer ` and never reads `IR.auth`. This was **status quo from v0** (v0's `codegen.ts` TS SDK never read it either — not a v1 regression). Decide here whether to unify (TS also reads `IR.auth`, with a leg) or document TS's deliberate divergence; either way the conformance auth row already passes because every target sets auth explicitly. (Python was in this outlier set until bit 14 c made it read `IR.auth` with the pair rule, leaving TS the only one.)

**Cross-SDK realtime auth-refresh sweep (surfaced bit 12 phase d).** Two related realtime-auth behaviors are deferred, consistent with TS: (1) `dialWebSocket` has no 401-refresh (TS's browser WebSocket can't either); (2) a realtime connection reuses its construction-time auth token across reconnects (v0 behavior) rather than picking up a token refreshed mid-connection. Neither is a conformance-grid cell (the reconnect cells test resume, not auth refresh). Decide at release whether to make reconnects use the current/refreshed token (and whether WS dials should 401-refresh) uniformly across SDKs, or document the per-target realtime-auth behavior. Note: this is distinct from the per-dial `X-Request-Id` (bit-12 Fd2), which is fixed.

**Cross-SDK close-event surface (surfaced bit 12 phase d).** A WebSocket close exposes `(code, reason)`. TS surfaces both through an `On("close")(code, reason)` handler; Go surfaces the reason through `On("close")(reason)` and both code and reason through the error `Read` returns (`errors.As` on `websocket.CloseError`, or `websocket.CloseStatus(err)`) — the idiomatic path, since coder/websocket itself has no close handler. Observable parity holds (both fields are reachable in each target), only the surface shape differs. Decide at release whether to unify on a handler shape or document the per-target surface; a Go `OnClose(code, reason)` handler was measured at +442 B and rejected in bit 12 as redundant with the error path.

**Cross-target test-driver read-after-failed-send (surfaced bit 13 phase e, Fe6).** The Rust conformance/harness driver's `observe_frames` stopped reading WebSocket frames after a send error, which can drop the observed close `(code, reason)` when a send loses the race with the server's close. Bit 13 fixed it (the driver reads on after a failed send; proven deterministically with a 12 MiB send after a 4401 close + hang-up, 25/25). Go's test driver has the **same limitation**; whether that is why Go's WS-D leg passes today is **unverified**. The sweep should confirm with the same deterministic send-after-close before applying the read-on fix to the Go driver. This is test-infrastructure, not SDK surface (+0 runtime).

**Cross-SDK untyped-enum-with-null (surfaced bit 14, IR-level).** An untyped `{ enum: [..., null] }` (no `type`) is a well-defined value set, but the IR seam (bit 09, `ir/schema.test.ts:99`) deliberately maps it to `{ kind: "unknown" }` ("an enum holding a null, unreadable"), so every SDK that reads only the IR (H2) emits the top type for it — Python `Any`, and by the same path Go/Rust/TS/C#/Java their own. A `type`-tagged nullable enum (`type: ["string","null"]`) still reads as a nullable literal union (`Literal["a"] | None`); only the untyped form degrades. Decide at the sweep whether bit 09 should read an untyped enum's non-null members as a literal union with the null as the nullable (a one-place IR change that improves every target at once), or document the untyped-enum degradation as deliberate. This is an IR-seam decision, not a per-emitter one; no SDK can recover it alone.

**Cross-SDK error-message text — reason phrase (surfaced bit 14 c, Fc2).** The error string (`str(e)` / `Message` / `Error()`) is `"HTTP <status>: <message>"` with no HTTP reason phrase in Python (Fc2: `http.HTTPStatus` wording drifts between the 3.11 floor and the 3.14 pin — 413/414/416/422 — so a phrase would make the text depend on the interpreter), C# recommends the same pending a probe of .NET phrase stability, and Java is **structurally forced** to it (`java.net.http.HttpResponse` exposes no reason phrase at all). Go and Rust print `"404 Not Found: <message>"` with the phrase. Decide at the sweep whether all SDKs drop the phrase (the determinism-safe choice three targets already take, two by necessity) or Go/Rust keep it as a documented per-target nicety; message text only — the conformance grid asserts status + semantics, not the phrase.

**Cross-SDK caller-client cross-origin auth strip (surfaced bit 14 c, Fc7).** When the caller supplies its own HTTP client, H18.10 (drop `Authorization` + configured headers on a cross-origin redirect) must still hold. Python (Fc7), C# and Java **enforce it** — the SDK owns the redirect follow loop, so it strips the caller client's headers/auth cross-origin regardless of what the caller set. Rust **documents that it cannot** (reqwest's `default_headers` can't be stripped after the builder). Decide at the sweep whether Rust moves to an SDK-driven follow loop to match (so the invariant holds for every target whatever the caller passes) or the Rust limitation stays documented. Security-relevant: without it, a hop to another origin carries the caller's credentials.

**Cross-SDK text charset decoding (surfaced bit 14 c).** A non-JSON text answer is decoded as UTF-8 regardless of the response's `charset` by Python, Go, TS, C# and Java (the SDK decodes the bytes itself); Rust honors the declared charset. Decide at the sweep whether to unify on UTF-8-regardless (the majority, and the common case) or have every SDK honor charset like Rust (correct for rare non-UTF-8 responses). Low-stakes (APIs are overwhelmingly UTF-8); document or unify.

**Cross-SDK response decompression (surfaced bit 15).** Python (httpx2's default `Accept-Encoding`, the cap counting decoded bytes), Go (net/http's default gzip), TS (undici) and C# (bit 15 phase c, Fc1: named gzip/deflate/brotli on its own handler, the cap counting decoded bytes) decompress transparently, and so does Java (bit 16 phase c2: gzip and deflate decoded by the SDK with the cap counting decoded bytes; brotli is never offered, because the JDK ships no brotli decoder); Rust alone is off (reqwest built without the compression features, no `Accept-Encoding`). 5-ON to 1-OFF, Rust the outlier; Java's ON set is gzip and deflate only. A caller-supplied handler (C#'s `HttpMessageHandler`) governs its own decompression. Decide at the sweep whether to unify (ON-with-decoded-caps across all, or OFF across all) or document Rust's divergence. Memory-safety holds for the ON targets because the **100 MiB response cap** counts decoded bytes, read in bounded buffers (8 MiB is the SSE event cap and 64 KiB the stream error-body cap, not the response cap). The bomb that moved Python to httpx2 was a decoder handing back one 64 MiB chunk of a 65 KB gzip; .NET's streaming decode into bounded reads avoids it by construction (bit 15 Q-c4).

**Cross-SDK HTTP protocol version (surfaced bit 16, Java).** `java.net.http.HttpClient` negotiates HTTP/2 by default (ALPN, HTTP/1.1 fallback), while C#'s `SocketsHttpHandler` and the other targets transact HTTP/1.1. The conformance grid asserts the observed wire, so an HTTP/2 frame layer could diverge Java's observed requests from every other target. Bit 16 pins `HttpRequest.version(HTTP_1_1)` in-emitter for grid alignment. Decide at the sweep whether all SDKs pin HTTP/1.1 (wire-identical, conformance-safe) or the grid accepts per-target HTTP/2 (letting each SDK use the better protocol where the server supports it). Only manifests against an HTTP/2-capable server; the reference server's capability is the gating fact to confirm.

**Cross-SDK header-rule parity gap (surfaced bit 14 c).** Python phase c pins two header rules no Rust (or Go) fixture exercises: a declared `Idempotency-Key` header param's value wins over the SDK-generated key, and an empty-map header-param value sends no header (a non-empty one its JSON text). The behavior is cross-SDK by design (the Rust/Go layer order would do the same), but it is **unpinned** in Rust/Go — a test-coverage parity gap, not a behavior divergence. The sweep should add the two legs to the Rust and Go fixtures so every SDK pins the rules.

**Cross-SDK stream-timeout granularity (surfaced bit 15 phase d, Fd8).** The per-call/config timeout bounds a different span of a streaming read per target: C# (`SocketsHttpHandler`) bounds the open up to the response headers, so an inter-event gap after the headers is not cut; Python (httpx) bounds connect, write and pool-acquire separately. Both honor the invariant that a mid-stream gap is not cut by the request timeout (the bit-15 d SSE legs pin it, as do Go/Rust/TS); only the span each timeout governs *before* the stream begins differs. Decide at the sweep whether to document the per-target granularity or align on one span. Low-stakes: the grid asserts the delivered events, not the timeout span.

**Cross-SDK caller-handler connection drain (surfaced bit 15 phase d).** C#'s SDK-owned handler sets `MaxResponseDrainSize = 0` (`runtime/csharp/Handler.cs:44`), so an abandoned response body is not drained and the connection closes at once; a **caller-supplied** `HttpMessageHandler` keeps its own default (a ~2 s drain, Q-d12 measured 2,005 ms), which the SDK leaves untouched. The other targets that own their transport drain nothing by the same reasoning, but a caller-supplied client is C#/Java-specific config. Decide at the sweep whether the caller-handler's drain stays the caller's responsibility (the current stance — the SDK sets only what it owns) or the SDK forces `MaxResponseDrainSize = 0` onto a caller handler too. Observable only as connection-reuse latency, never as answer content.

**Cross-target test-driver non-JSON realtime send (surfaced bit 15 phase d, #10).** On conformance cell #10 (a realtime send of a non-JSON payload) the C# test driver sends raw text where the Python test driver sends a JSON string — a divergence in the test drivers, not the SDKs. This joins the test-driver divergences list beside the Rust/Go read-after-failed-send above (Fe6). Test-infrastructure only (+0 runtime); the sweep should confirm both drivers drive the same SDK send path before unifying the driver shape.

**Cross-SDK non-ASCII wire escaping (surfaced bit 15 phase d).** C# alone escapes non-ASCII characters in a JSON body on the wire (`"é"` is sent as `"é"`): the source-generated `System.Text.Json` path keeps STJ's default escaping, and `JsonSourceGenerationOptions` (`emit/csharp/json.ts:122`) exposes no encoder knob to relax it, while Python, Rust, Go and TS send raw UTF-8. It is **invisible to the conformance grid**, which compares parsed meaning, not wire bytes (`é` and the raw UTF-8 bytes both parse to `é`). Decide at the sweep between giving the C# serializer a relaxed/custom encoder — which the source-gen attribute cannot express, so it needs a serializer-options path and costs runtime bytes — and documenting C#'s escaped wire as a benign, spec-valid divergence. The escaped pin stands until then.

**Cross-SDK bounded streaming-read property (surfaced bit 15 phase d, M5).** A streaming read delivers a completed event that arrives before an over-cap event, and never buffers the whole stream to find the cap violation — the cap is enforced per bounded buffer, not by reading the whole chunk first. In C# this is equivalent-under-test to a cap-after-drop mutant (M5) unless a whole-chunk read is forced, so it was honestly recorded as equivalent in phase d rather than hollow-killed, and the property is deferred here. The sweep should add one leg per SDK (a completed event is delivered before an over-cap one; the whole stream is never buffered) so every target pins the bounded-read guarantee, not merely the cap value. **Java is done (bit 16 d1):** its parser reads at most 64 KiB at a time, on demand (it reads only once every completed event is handed out, which a leg pins against a read-ahead mutant). It raises the 1 MiB line cap and the 8 MiB event cap within one read of crossing them (refused at 2/9 MiB against endless input, not at 64 MiB). Under on-demand reads, a cap-before-completed-events mutant is equivalent, so the outcome leg pins it.

**Cross-SDK SSE resume id — delivered vs parsed (surfaced bit 15 phase d, #4).** On an SSE reconnect C# resumes from the last **delivered** event's id (the id of the event handed to the caller), while Python, Go, Rust and TS resume from the last **parsed** id (updated as soon as an `id:` line is read, before the event is dispatched). The two differ only when the stream breaks between parsing an `id:` line and delivering its event: C# then re-requests from the last event the caller actually saw, which is arguably the more correct resume point (no undelivered event is skipped). Decide at the sweep whether to align the others to last-delivered (C#'s shape) or document the per-target resume semantics; both satisfy the conformance resume cells, which do not break mid-event.

**Cross-SDK request_start clock origin (surfaced bit 15 phase e, Fe7).** Every target logs an integer `duration_ms` on the `request_start` on_log/OnLog entry, but where the call's clock starts differs. TS (`runtime/ts/hooks.ts:69`, a literal `0`), Go (`runtime/go/request.go:84`, the unset zero value) and C# (`runtime/csharp/Log.cs`, after Fe7 c9d6655 — the clock starts in `Start()`, at `request_start`) all log **0**. Rust (`runtime/rust/log.rs:40,57` — `start: Instant::now()` in `CallLog::new`, `self.start.elapsed()` in `emit`) and Python (`runtime/python/log.py:29,38` — `time.monotonic()` from `__init__`) read **elapsed since `CallLog` construction** (`exchange.rs:117`, before `started()` at :122), so their `request_start` can carry a non-zero value. Rust's and Python's harness legs pin `0` (`rust-harness.test.ts:274`, `python-harness.test.ts:432`) but were never load-certified — the same construction-to-start gap put C#'s `request_start` at up to 54 ms on a cold first call under load (Q-e4: 15 of 20 loaded runs > 0), which is exactly the shape Fe7 fixed in C#. Latent; not yet observed red for Rust or Python. Decide at the sweep whether to unify on "`request_start` logs `0`, the call's clock starts there" for Rust and Python too (a one-line change per runtime with a named G14 delta each, red-first) so "milliseconds since `request_start`" holds everywhere, or load-certify their pin and document "elapsed since the call object". Invisible to the conformance grid (it asserts events and status, not the log duration); the recommended resolution is to unify.

**Cross-target WS bogus-token send (surfaced bit 15 phase e, Fe8).** On the `?token=` 4401-refusal WebSocket leg (WS-D), whether the driver sends a message into the refused socket diverges: Rust (`rust-harness.test.ts:377-378`) and Go (`go-harness.test.ts:356`) **send** (ported from v0), while Python (its Fe8) and C# (our Fe8) **do not**. The send pins nothing — Q-e5 ran both variants 20× under load on C# and all 20 were identical (close `4401 unauthorized`, 0 yields, one hop): it is a race into a closing socket. The deterministic send-failure path is pinned instead in C#'s default run (a 12 MiB send against `hangUp` 4401, `closedBy {4401, unauthorized}` with the error traced — `sdk.driver.stream.test.ts`, contract 50 §4.4). Decide at the sweep whether to drop the send from the Rust and Go drivers for parity, or to pin a refused socket's send outcome somewhere other than C#'s default run. Test-infrastructure only (joins the test-driver divergence list beside the Fe6 read-after-failed-send above; +0 runtime).

**Cross-SDK safe mode on the grid (surfaced bit 15 phase e).** TS runs the conformance grid in safe mode as well as throwing (`ts.test.ts:165-175`); C#'s runner, like Rust's, Go's and Python's, runs the **throwing client alone** (`bits/15`:37). C# covers safe mode in the default run instead — the `http-safe` and `fixtures-safe` fixtures, in both `throwOnError` modes, over the emitted SDK's build and its `SdkResult` paths. Decide at the sweep whether the grid should run every target's safe-mode client (a second client per cell per target, roughly doubling harness time) or record that safe mode is a default-run concern outside TS. Grid impact: safe-mode wire behavior is grid-proven only for TS.

**Cross-SDK Host/Connection override (surfaced bit 16 phase c2, Qc6).** Java cannot send a caller's `Host`, `Connection`, `Content-Length`, `Expect` or `Upgrade` header: `java.net.http.HttpClient` refuses them unless the process-global `jdk.httpclient.allowRestrictedHeaders` property is set, and a library must not set process-global state. The Java SDK refuses each by name as `ConfigException` before anything is sent (`http.wire.test.ts`, which also pins that the property stays unset). The other targets let a caller override `Host`. Decide at the sweep whether to document Java's refusal as a permanent per-target limitation (recommended, since no in-library fix exists) or have every SDK refuse a caller `Host`/`Connection` for parity.

**Cross-SDK header value and name validation (surfaced bit 16 phase c2).** Java refuses a header value holding any control character (`\u0001`, `\u007f`, as well as CR/LF/NUL) and a header name that is not a token (`"bad name"`) as a cause-less `ConfigException` naming only the header, with nothing sent. The JDK's own refusal quotes the value, so the SDK deliberately sets no cause, which would leak a secret value. C# checks only CR/LF/NUL on the final map. It sends `\u0001`/`\u007f` raw (`TryAddWithoutValidation`), so the server's 400 surfaces as `BadRequestException`, and it silently drops an invalid name (the call answers 200; probe `~/.cache/honey-tmp/b16c2/b3/csharp-header-probe.txt`). Recommended: C# (and any other target found lax in the sweep) refuses both before sending, as `ConfigException` with the value kept out of the message, red-first per target. Security-adjacent: a silently dropped header can drop a credential the caller believes was sent.

**Cross-SDK unclosed stream holds its connection (surfaced bit 16 d1, F1/F3).** In Java, C# (Fd9) and Go, a stream that is never closed, read to its end, errored or canceled keeps its connection until the process exits. No SDK registers a GC-driven release: on JDK 21 an unclosed body survived two `System.gc()` calls, and such a release would be nondeterministic, testable only by forcing GC. Java adds one sharp edge: a for-each `break` over an `EventStream` cannot release it (the JLS has no iterator close hook), so the emitted javadoc tells callers to use try-with-resources, and a leg pins the sentence. Decide at the sweep whether every SDK documents the close obligation identically, or whether any target can offer a deterministic scope-bound release.

**Cross-SDK stream cancel carrier (surfaced bit 16 d1, F2/F4).** C#'s cancellation token bounds the open and the whole stream from any task, and its draining handler and per-read token have no Java carrier. Java's cancel is an interrupt of the reading thread (`CancellationException`), and `close()` from any thread ends a pending read quietly. Context: JDK 17's own `BodySubscribers.ofInputStream` ignores an interrupt under a pending read (it stays blocked until the server closes; measured, b16d/probe/jdks.log), so the Java SDK reads every stream through its own Flow pump, whose `take()` is interruptible on 17/21/25, and the release legs run on 17 explicitly. Document the per-target cancel model at the sweep; the grid asserts outcomes, not the carrier.

**Cross-SDK WebSocket client close codes (surfaced bit 16 d2a, W20).** The JDK's `WebSocket.sendClose` accepts only 1000, 1001, 1008, 1011 and 3000–4999 from a client on 17/21/25; any other code fails the returned future with `IllegalArgumentException` (verified by both sessions). So Java closes an over-cap message with **1008** "Message too big", where C# and the others send 1009. It echoes a server close whose code a client can't send (1002, 1003, 1007, 1009, 1010, 1012–1015, or a 1005 with no status) as 1000 with the server's reason, while `closedBy` keeps the server's real code. A caller's `close(status)` with such a code is a cause-less `ConfigException` listing the legal set, with no frame sent and the socket left usable; C# sends any valid code. The grid asserts no 1009. Decide at the sweep whether every SDK uses 1008 for the cap (one wire code everywhere) or the per-target codes stay documented.

**Cross-SDK WebSocket keepalive and send gate (surfaced bit 16 d2a, W14/W17/W19, K8).** The JDK's WebSocket sends no keepalive pings, and it refuses a second outstanding data send ("Send pending"). A ping or close issued behind a pending data send breaks the socket nondeterministically (9 runs across 3 JDKs). So the Java SDK owns what .NET's BCL owns for C#: a send gate that every frame passes through (data, ping, close echo, cap close), and a 20 s keepalive (C# parity) whose ping waits behind a pending send. Its pong clock starts when the ping is actually sent, so a slow upload longer than 20 s isn't read as a dead peer. .NET interleaves the ping inside a send. These are behavior notes; no unify decision is needed unless another target lacks a keepalive.

**Java WebSocket handshake visibility (surfaced bit 16 d2a, K4/K10).** `java.net.http.WebSocket` exposes neither the 101 response nor its headers, so a dial's `RawResponse` has status 101 and the ws:// URL with empty headers, where C# fills them (K10). A server's bad `Sec-WebSocket-Accept` is refused by the JDK itself as a 101 with a null message, so the SDK fails closed (a HoneyException, nothing delivered) but can't name that reason (K4). An unoffered subprotocol is named, because the SDK checks it itself. Document both as JDK limits.

**Java realtime cancel model (surfaced bit 16 d2b, R3).** Java has no cancellation token, so a realtime call has no method token whose later cancel closes the connection. `close()` is the end. An interrupt of the reading thread is a cancel-safe read cancel: the transport is dropped and the connection is left RECONNECTING with its cursor. So after an interrupt `provenTransport` reads null, where C#'s closing token keeps it. Document the model per target; the grid asserts the cursor and state, not the proven transport after a cancel.

**Java realtime open bound and close (surfaced bit 16 d2b, R4).** C# bounds each open with `CancelAfter(30 s)` and links its closing token into every reconnect. Java owns both mechanisms:
- a timer interrupts the opening thread only while it still opens, under a lock;
- `close()` stops a pending open the same way;
- the opener clears only the interrupt it set, so a caller's own interrupt is never taken;
- a bound ends the open as `ApiTimeoutException`, a close as a null read.

A caller-supplied adapter that swallows interrupts isn't bounded until it returns; a late open is then closed and the open times out. The start-of-open closing check is the load half of a volatile store-then-load handshake with `close()`. Its mutant survives because no leg can schedule a close into that few-instruction window; this is a reviewer-ruled race guard, not dead code. The backoff is capped at the open bound (C# `RealtimeLoop.cs:131`).

**Realtime session send encoding (surfaced bit 16 d2b).** Java's Jackson writes non-ASCII in a session send as UTF-8, as Python does; C#'s System.Text.Json escapes it as `\uXXXX`. Both are valid JSON. Decide at the sweep whether the grid pins one wire form or asserts the decoded value only.

**Bit 17 carry-ins (the CLI close).**
- `honey-codegen generate --app`: generate from an app module, not only a JSON `--spec`. Needs core's public document entry and a no-bind codegen flag first; `src/ir/load.ts` and regression V072-2 moved here with it (files.tsv rows at 19).

- CLI release signing and attestation: the emitted goreleaser config and release workflow (least-privilege) ship unsigned; decide on cosign/SLSA attestation of the archives and checksums, and whether the install scripts verify them.
- Security sweep, help text: the CLI strips control characters from spec text through `helpText` (title, summaries, descriptions, the skill) and escapes DEL and C1 in its JSON output, and refuses binary bytes to a terminal (F2, pinned at bit 17 i on a built binary). Sweep every SDK's emitted doc comments and help for the same control-character and DEL/C1 handling.
- Go SDK dial hooks: the ws and realtime dials skip the `OnRequest`/`OnResponse` hooks (`runtime/go/ws.go:54`, `transport.go:156`, `transport_sse.go:36`, `transport_longpoll.go:67`), so a hook never sees a dial. - Core stream routes emit no 2xx response in the document (kitchen `/api/events` and `/api/events-live`), so generated clients infer the stream from the route kind alone. Decide whether core emits the 2xx with its `text/event-stream` media type.
